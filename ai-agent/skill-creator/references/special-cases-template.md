# SPECIAL_CASES.md — Gotcha 收集模板

> **Purpose:** 集中收集边界情况、常见错误、模型假设偏差。
> **原则:** 每个 gotcha 回答一个问题：**"没有这条指令，模型会做什么错误的默认行为？"**

---

## 格式规范

每个 gotcha 用以下格式：

```
## [Gotcha 标题]

**错误默认行为：** <模型会做什么>

**触发条件：** <在什么情况下发生>

**正确行为：** <应该怎么做>
```

**示例：**

```
## API 返回空数组时模型会继续空等

**错误默认行为：** 模型认为"有空结果=任务完成"，直接返回

**触发条件：** 外部 API（如搜索、数据库）返回空数组 [] 而非错误

**正确行为：** 检查结果数组长度。若为 0，记录"无结果"并继续下一步，而非提前结束
```

---

## Gotcha 收集清单（每个 skill 创建时必填）

对于每个主要步骤，问自己：

- [ ] **输入边界：** 模型的输入在什么极端情况下会失效？（空输入、超大输入、格式错误的输入）
- [ ] **工具假设：** 模型调用工具时会做什么错误假设？（参数顺序、认证状态、权限边界）
- [ ] **时序依赖：** 模型会假设什么顺序执行，而实际顺序可能不同？
- [ ] **确认偏误：** 模型在什么情况下会"自信地"输出错误结果而不自知？
- [ ] **上下文丢失：** 模型在长对话的什么位置会遗忘关键指令？

---

## 优先级

| 优先级 | 类型 | 描述 |
|---|---|---|
| **P0** | 硬性错误 | 模型会执行但结果完全错误，且无报错 |
| **P1** | 质量退化 | 模型输出可用但远低于最佳质量 |
| **P2** | 效率损失 | 模型做对了但用了过多 token/迭代 |

---

## 写作原则

1. **不要**写"请注意..."、"警告..."等模糊开头——直接描述错误行为
2. **不要**解释为什么模型会犯错——只描述**什么错**和**怎么对**
3. **要**用具体数字/阈值——"超过 30 秒" 而非 "超时"
4. **要**引用具体工具或 API——"Notion API 返回 429" 而非 "API 错误"
